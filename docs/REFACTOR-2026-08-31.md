## 1. Data layer: one file per entity

**Finding §2.1.** `queries/` and `mutations/` are gone. `src/api/` is transport only;
nothing entity-shaped survives there, so "where does this hook go" has exactly one answer.

```
src/api/
  client.ts                    axios instance + both interceptors
  keys.ts                      household-rooted key helper
  queryClient.ts               defaults, incl. the 5xx-only retry predicate
  useInvalidatingMutation.ts   a write plus the reads it makes stale

src/modules/financial/api/expenses.ts     keys + read + create + delete, one screen
src/modules/settings/api/categories.ts    ONE key, ONE type, ONE hook
src/modules/settings/api/accounts.ts      ONE key, ONE type, ONE hook
src/modules/settings/api/members.ts       members + users, both invalidated together
src/modules/settings/api/prefs.ts
src/modules/auth/api/session.ts           session + login
```

Entities live in the module that owns the **write** side: `financial` owns Expense,
`settings` owns Category/Account/Member/Prefs, `auth` owns Session. `financial` importing
`@/modules/settings/api/categories` is a deliberate consumer→owner edge — it is what forces
the single source of truth that findings §1.2 needed.

### 1.1 Query keys rooted at the household

`src/api/keys.ts`:

```ts
householdKey(hid)          → ['h', hid]
entityKey(hid, 'expenses') → ['h', hid, 'expenses']
```

Every household-scoped key extends it, so one call drops a whole tenant's cache — on
sign-out, or when a household switcher ships. Previously each entity invented its own root
(`['expenses', …]`, `['categories', …]`, `['users', …]`) and there was no way to express
"everything for household X".

### 1.2 The rule that makes findings §1.2 unrepeatable

> **One endpoint → one query key → one response type.**

Where two surfaces need the same rows shaped differently, that is a `select` on one hook,
never a second hook:

```ts
useCategories(hid) // all rows — the settings list, which needs archived ones
useActiveCategories(hid) // same key, same fetch, select: filter(!archivedAt)
```

Same for accounts. `staleTime: Infinity` is gone from both — it was what turned a missed
invalidation into a session-long stale read.

`/users` and `/households/:id/members` are genuinely different endpoints, so they keep
separate keys but live in one file and share one invalidation set:

```ts
const peopleKeys = (hid) => [memberKeys.all(hid), userKeys.all(hid)]
```

`useInvalidatingMutation` takes a **list** of keys for exactly this reason, and returns the
mutation object untouched so `error` and `isPending` reach the caller (finding §2.5).

### 1.3 Optimistic writes

`useCreateExpense` now:

- writes only into caches whose filters actually match the row — the filters object is read
  back out of the query key (`FILTERS_IN_KEY = 4`) and checked with `matchesFilters()`
  (finding §2.2)
- moves `totals` alongside `pagination.total`, recomputing `average` (finding §2.2)
- uses `crypto.randomUUID()` for the placeholder id (finding §2.3)
- exports `isOptimisticId()`, which `ExpenseTape` uses to suppress manage actions on rows
  the server has not acknowledged

`useDeleteExpense` gained the whole cycle it was missing: `cancelQueries`, optimistic
removal with `withoutRow()` (which also decrements the aggregates), full rollback in
`onError`, and a visible error at the call site. `ExpensesPage` renders it, and the delete
is behind `ConfirmDialog` (finding §1.5).

### 1.4 The wire shape is written out

`toRequestParams(filters)` replaces `params: filters`. The internal names and the query
names had already drifted apart once — `sortOrder` vs `order`, findings §5.2 — and a silent
mismatch there reads as a control that works and does nothing.

> ⚠️ This function is also the single place the snake_case conversion will land. See
> [`API-GAP-ANALYSIS.md` §2.2](API-GAP-ANALYSIS.md#22-casing-camelcase-vs-snake_case).

### 1.5 Retry predicate

`queryClient.ts` retries only 5xx and network failures, at most twice; mutations do not
retry (finding §2.4). A 401 now fires the interceptor redirect once instead of three times
into an unloading page.

## 2. Types and enums separated

**Findings §3.1–§3.9.**

```
src/types/            cross-module domain
  api.ts              ApiErrorBody, Pagination, Paginated<T>, Totals
  catalog.ts          Category, Account, AccountKind   ← read by financial, written by settings
  expense.ts          Expense, CreateExpenseInput, ExpenseFilters,
                      ExpenseSortField, SortDirection
  household.ts        Role, User, Household, Session

src/theme/rims.ts     RIM_COUNT, RimIndex, rimFor, RIM_CLASS
src/utils/validators.ts   isAsciiEmail — one definition

src/modules/auth/types/auth.ts            LoginInput, SigninErrorKind, SigninState,
                                          LandingReason, SigninResult
src/modules/financial/types/ledger.ts     DayGroup, DayTotal
src/modules/financial/types/baseline.ts   Baseline, Verdict
src/modules/settings/types/settings.ts    Member, MemberStatus, MemberDeletionReason,
                                          HouseholdPrefs, CategoryInput, AccountInput,
                                          InviteInput
src/modules/settings/lib/memberStatus.ts  memberStatus(), MAX_RESENDS
```

**Placement rule:** cross-module domain types in `src/types/`; module-scoped types in
`src/modules/<module>/types/`; component `Props` local to the component.

**Deliberately not moved:** all 18 component `Props` interfaces. They are local and
imported by nobody — relocating them would be churn and would make each component harder to
read.

**Deleted rather than kept:** `src/types/index.ts` and `src/api/types.ts`. Both had zero
importers, deep imports were already the convention at all 30 call sites, and keeping both a
barrel and deep imports guarantees three import styles for one type. `src/types/settings.ts`
is gone — it was neither types-only nor global.

`Category` and `Account` went to `src/types/catalog.ts` rather than into the settings module
precisely because `financial` reads them on every ledger row. `Category` absorbed
`ExpenseType` and `Account` absorbed `PaymentSource`; the duplicate pairs were the modelling
error behind findings §1.2 and §3.4.

**`src/theme/rims.ts`** ends three separate problems at once: the triplicated `RIM_CLASS`
(one copy of which had only 4 entries), the two disagreeing derivations (`rimFor(order)` vs
`rimOf(typeId)` over 4 rims), and the index-based callers. There is now one `rimFor(order)`
keyed on the stable `order` field, used everywhere.

**New named types:** `ExpenseSortField` and `SortDirection` (finding §3.8),
`MemberDeletionReason`. `isThemeId` is now used instead of a cast, and `isLang` was added to
`src/i18n/locales.ts` for the same reason (finding §3.10).

## 5. MSW split by context

**Findings §5.1–§5.7.**

```
src/mocks/
  db.ts                the ONLY mutable store + resetMockState + nextId
  fixtures/            household, members, categories, accounts, expenses, prefs
  handlers/            auth, expenses, categories, accounts, members, prefs
                       + shared.ts (envelope, latency) + index.ts (barrel)
  browser.ts           unchanged
  server.ts            unchanged
```

**The design constraint: split the seeders, keep the store singular.** Handlers mutate `db`
in place (`db.expenses.unshift`, `member.resendCount += 1`), so per-context stores would
hand each handler file its own copy and quietly break both cross-context behaviour and
`resetMockState`. `fixtures/*` export **pure seed functions only** — that is what makes the
split safe. ESM module singletons then guarantee one store per process.

`browser.ts` and `server.ts` did not change: `@/mocks/handlers` resolves to
`handlers/index.ts`. Only `src/test/setup.ts` moved one import (`@/mocks/data` →
`@/mocks/db`).

### React Compiler lint

The repo has `react-hooks` compiler rules enabled. Two first attempts were rejected and
rewritten:

- **`onChangeRef.current = onChange` during render** (`refs` rule) and **`setState` inside an
  effect** (`set-state-in-effect`) → the debounce now lives in the change handler with a
  timer ref touched only in handlers and a cleanup effect, and the external-value sync uses
  the documented adjust-during-render pattern.
- **Closure caches mutated after render** (`immutability`) in `useItemBaselines` → replaced
  with eagerly built Maps returned from `useMemo`, `useCallback` for the accessors, and a
  module-level `NO_ROWS` so "no history" is referentially stable too.
